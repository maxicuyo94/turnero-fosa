# Seguridad y despliegue

Revisión del 9 de octubre de 2026. Los cambios están preparados para el proyecto existente; las credenciales y los permisos de producción deben configurarse en el proveedor. La web pública permite reservar y comprar sin crear una cuenta. El panel exige sesión y comprueba el usuario, el rol y la versión de sesión en cada página y acción.

| Requisito | Implementación y alcance |
| --- | --- |
| Ocultar keys y eliminar secretos de Git | `.env*` ignorados; DB y composición marcadas `server-only`; escaneo del código, blobs de todas las referencias Git locales y bundles del navegador con valores redactados. No se encontraron credenciales reales mediante ese escaneo. Solo se exceptúan dos URLs sintéticas verificadas de un test. No se reescribió el historial porque no se detectaron secretos reales. |
| Key pública de DB | No corresponde: PostgreSQL/Prisma se usa exclusivamente en el servidor. Nunca publicar `DATABASE_URL` ni crear una variable `NEXT_PUBLIC_DATABASE_URL`. Solo la URL de la app y la site key de Turnstile son públicas. |
| RLS | Migraciones habilitan RLS en las 30 tablas operativas, incluido el catálogo ampliado. Solo `fosa_backend` tiene política de acceso. Los roles de navegador, si existen, no reciben permisos. El backend autorizado puede operar todas las filas del taller; las restricciones por sesión y enlace privado se aplican además en el servidor. No es aislamiento entre talleres o tenants. |
| Cifrado | AES-256-GCM con nonce aleatorio y autenticación del campo para destinatario, asunto, cuerpo y errores de correos, y nombre/contacto/dirección de pedidos. Las contraseñas y tokens de cancelación/pedido se hashean. Los datos de clientes, vehículos e historial de turnos siguen siendo consultables en la DB: requieren cifrado de almacenamiento/backups del proveedor; no se afirma cifrado de aplicación de todos esos campos. |
| Autenticación y registros | `requireStaff()` reconsulta cuenta y rol, y revoca sesiones por versión. Cambios de configuración exigen ADMIN. El público consulta por código o token privado; no recibe contacto ni hashes. Las consultas de enlaces privados y los reintentos de pago tienen presupuesto compartido en PostgreSQL. |
| Bloquear manipulación de campos | Acciones toman campos permitidos; checkout y líneas de carrito rechazan campos desconocidos. Precios, envío, estado, stock y duración autorizada se calculan o verifican en el servidor. La identidad del operador proviene de la sesión. |
| Cookies | JWT cifrado por Auth.js, duración de 8 horas, cookie `__Host-authjs.session-token` en producción, `Secure`, `HttpOnly`, `SameSite=Lax`, sin Domain y con Path `/`. Se conservan las protecciones CSRF de Auth.js y Server Actions. |
| Contraseñas | Scrypt con sal aleatoria, comparación de tiempo constante, trabajo equivalente para usuarios inexistentes; longitud máxima de 128 y formato de hash validado. |
| Rate limiting | Contadores persistentes y atómicos para login, reservas, recuperación, tienda y consultas públicas. Las reservas sin IP usan presupuesto compartido. En Vercel se usa `x-vercel-forwarded-for`; en otros hosts el proxy debe sobrescribir las cabeceras de IP. |
| Bots | Honeypot y Turnstile en reservas, recuperación y compra; validación del token en el servidor, con acción y hostname exactos, tiempo límite y rechazo ante errores. Sin secreto, producción rechaza esos formularios públicos; desarrollo permite pruebas locales. |
| Consultas e inputs | Prisma y SQL con parámetros para solicitudes. Validación con Zod y límites de tamaño; autorización al comienzo de cada acción interna. |
| Sanitización | React representa datos como texto escapado, sin `dangerouslySetInnerHTML`. URLs de contacto y pagos se validan. Logs de errores no imprimen mensajes ni payloads de proveedores/Prisma. No se incorpora HTML arbitrario. |
| Archivos | Solo Excel autenticado, extensión/MIME permitidos, 3 MB comprimidos, 20 MB expandidos, 200 entradas ZIP, 1.000 productos, filas/columnas acotadas; se bloquean macros, enlaces externos, objetos embebidos y rutas de traversal. Se valida la expansión real antes de ExcelJS. Fórmulas no se ejecutan: solo se aceptan resultados numéricos ya calculados. No se publican archivos cargados. |
| Minimizar respuestas | DTOs públicos sin contacto, ubicaciones internas ni hashes. Pedidos internos omiten hash del enlace y claves de idempotencia antes de renderizar. |
| Headers | CSP con nonce de cada respuesta, sin eval en producción; bloqueo de marcos y objetos, `nosniff`, Permissions-Policy compatible con el lector de cámara, referrer `no-referrer`, no-store/noindex en páginas privadas. La CSP requiere renderizado dinámico. |
| HTTPS | Redirección 308 en páginas/API y HSTS; el hosting debe forzar HTTPS también en estáticos. En hosting propio, terminar TLS y redirigir HTTP en el ingress, sobrescribiendo `x-forwarded-proto`. PostgreSQL en producción exige `sslmode` con TLS. |
| Dependencias | Auditoría de producción sin vulnerabilidades conocidas al revisar. Auditoría completa detecta `GHSA-vfj7-8cjw-p6xm` en `braces` de la herramienta de desarrollo OpenSpec, sin versión corregida. No se ignora ni se declara corregida; no está en las dependencias de producción. |

## Activación en hosting y base de datos

1. Generar `DATA_ENCRYPTION_KEY` con 32 bytes aleatorios en hexadecimal y guardarla en el gestor de secretos. Conservar una copia protegida: perderla impide recuperar los datos cifrados. No reemplazarla para rotar sin un proceso de descifrado/recifrado. No usar `AUTH_SECRET` como clave de datos.
2. Crear el widget Turnstile para el dominio real. Configurar `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` y, para previews, `TURNSTILE_ALLOWED_HOSTNAME`. La clave pública debe estar presente al compilar el frontend. Registrar por separado dominios de producción y preview.
3. Configurar `AUTH_SECRET` y `CRON_SECRET` con secretos aleatorios de al menos 32 caracteres, además de las claves de proveedores del `.env.example`. Si alguna credencial fue expuesta fuera de este repositorio, revocarla y generar otra en su proveedor.
4. Separar conexiones: `MIGRATION_DATABASE_URL` usa el propietario para migraciones; `DATABASE_URL` usa un login nuevo sin superusuario, BYPASSRLS, propiedad de tablas o membresía en roles propietarios. Ambas deben usar TLS en producción. Aplicar `pnpm db:migrate` con el propietario; requiere permiso CREATE ROLE para crear `fosa_backend`.
5. Desde la consola administrativa del proveedor, otorgar **solo** la membresía `fosa_backend` al login de aplicación. Por ejemplo, para un login previamente creado `fosa_runtime`: `GRANT fosa_backend TO fosa_runtime;`. Nunca otorgar membresía de propietario, DDL, TRUNCATE o BYPASSRLS. No reutilizar el login de migraciones en `DATABASE_URL`.
6. Con la clave disponible y una copia de seguridad, ejecutar `pnpm security:encrypt-data` en el entorno correspondiente para convertir correos y contactos de pedidos históricos. Es paginado, evita sobrescribir cambios concurrentes y puede repetirse. Las escrituras nuevas ya se cifran; las antiguas se leen durante la transición.
7. Ejecutar `pnpm release:check -- --env=RUTA_LOCAL_PRIVADA`, `pnpm security:secrets`, `pnpm security:audit` y `pnpm security:audit:all`. La revisión de lanzamiento comprueba RLS y los privilegios del login de aplicación; ejecutar con el propietario debe mostrar pendiente. Verificar cifrado de discos/backups y HTTPS en el proveedor.

## Verificación

Pruebas de cifrado/autenticidad, validación contra bots, campos manipulados, hashes malformados y archivos hostiles están en `tests/security.test.ts` y `tests/xlsx-security.test.ts`. Las pruebas con PostgreSQL en `tests/database-security-prisma.test.ts` verifican RLS contra un rol ajeno y que el backend no pueda truncar; el rol de prueba se revierte dentro de una transacción. Usar exclusivamente una DB local/de pruebas para `pnpm test`.

Verificación local completada: 331 pruebas unitarias, 108 pruebas con PostgreSQL y 2 pruebas de navegador. RLS se aplicó y se verificó en la base local; lint y compilación de producción pasaron. La compilación se validó con una URL de DB configurada para TLS, sin acreditar una conexión TLS real al PostgreSQL local. Ninguna de estas comprobaciones acredita configuración ni despliegue de producción.

El workflow `security.yml` vuelve a escanear secretos, dependencias de producción y pruebas de seguridad en pushes/PRs. El escáner por patrones no demuestra ausencia de todas las clases de secretos y solo inspecciona referencias Git presentes localmente; conviene complementar con el secret scanning del proveedor de Git.

Referencias: [seguridad de Next.js](https://nextjs.org/docs/app/guides/data-security), [RLS de PostgreSQL](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [validación de Turnstile](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [aviso de braces](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).
